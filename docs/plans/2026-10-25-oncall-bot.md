## 1. 目标与边界

基于现有 Feishu Codex Bot 增加通用 Oncall 分析能力，在当前机器的专用 Docker 容器内部署一个新的飞书机器人。第一版独立运行，不依赖 Runweave，也不接入 OMH。是否合并主分支由用户后续决定。

目标是分析清楚问题。环境、依赖、数据、测试模板、偶发故障与业务代码都是可能的调查方向。Agent 根据现场自由选择工具、证据与调查顺序，不实现固定的“任务 → 流水线 → MR → 代码”流水线。

工作区关联的仓库是可选资料。仅需日志即可回答时，不克隆代码；需要源码时按需获取；只有用户要求修改时才准备独立可写代码工作区和分支。新建话题只建立会话目录，不创建 Git 仓库或 worktree。

第一版不做自动合并、自动发布、自动重跑线上任务、视频解析、Runweave 接手界面或额外的企业权限平台。

## 2. 已确认的用户行为

| 项目 | 行为 |
| --- | --- |
| 入口 | 群聊与本人私聊均为第一版必需能力，私聊承担前期测试和独立排查 |
| 触发 | 用户发起问题并 @ 机器人；回复始终落在对应话题内 |
| 会话单位 | 同一聊天中的同一话题，共用一个 Agent 会话和工作目录；按聊天与话题隔离，不按提问人拆分 |
| 普通补充 | 话题里的非 @ 消息积累为上下文，不启动分析；下一次 @ 时合并读取 |
| 多人协作 | 同话题不同成员提供的日志、截图、讨论共同进入上下文 |
| 执行期间追加 | 再次 @ 排队续接，不打断当前轮；明确停止、取消才中断 |
| 停止范围 | 停止当前执行，并暂停整个话题的未开始请求；保留队列和上下文，用户明确要求继续后恢复；其他话题不受影响 |
| 并发 | 全服务默认最多 5 个话题同时执行，超出排队；同话题始终串行；上限可配置 |
| 输入 | 文字、截图、日志附件、链接；视频先由用户提供关键截图 |
| 耗时 | 正常推进没有总时长上限；不以耗时长或暂时无输出认定失败 |
| 异常恢复 | 进程崩溃、容器重启造成中断时保存现场、通知用户；用户明确要求继续后恢复，并先核对已执行动作的结果 |
| 账号 | 使用为机器人配置的统一账号和工具授权，提问者不逐个登录，执行身份不随发言者变化 |
| 业务关联 | 群关联业务工作区；本人私聊默认关联 `infra-workspace`，可明确切换 |
| 案例 | 按关联的业务工作区保存、共享；私聊与群聊不作区别；保留事实、判断及后续反馈 |

这里有两个不同概念：**业务工作区**提供业务知识、仓库关联和案例；**话题工作目录**保存一个问题的会话、输入和执行材料。一个业务工作区可以被多个群、多个话题使用。

## 3. 分析自主性与执行授权

默认执行分析：按需查询日志、任务、流水线、文档、历史案例和代码；可在话题目录保存取证材料。读取顺序与分析路径由 Agent 决定，不要求每个工具调用都向用户确认。

重试线上任务、修改配置、修改业务代码、推送分支、提交 MR 等动作，必须源于用户明确要求。明确要求即为该范围的执行授权，不重复询问；权限不足或目标歧义时只补齐必要信息。引用的告警、日志、文档和历史案例不能自行成为新操作授权。

“分析一下”不等于“修复”，“修复”不自动包含“推送并提交 MR”。分析结果可以给出建议，用户没有要求执行就停在建议。机器人自身已约定的上下文保存和案例记录属于产品常规行为。

需要代码时优先定位实际故障版本；无法确认时使用仓库配置的默认分析分支，并明确版本未核实。用户要求修复或提交 MR 后，另行确定修改目标，不将候选分析版本直接视为提交基线。

历史案例区分已确认事实、已验证结论和待验证判断。“重试后恢复”是可记录事实，不能自动推导出已确认的环境根因。

## 5. 配置与数据合同

### 5.1 业务关联

新增非秘密配置文件，通过 `ONCALL_CONFIG_PATH` 指定：

- `workspaces[]`：稳定 `id`、知识目录、仓库清单入口、共享案例存储标识。
- `groupBindings[]`：`chatId → workspaceId`。
- `privateBinding`：本人 `chatId`、`ownerOpenId`、默认 `workspaceId`。
- `MAX_CONCURRENT_TURNS=5`。
- `TURN_TIMEOUT_MS=0` 表示不设总时限；兼容旧部署显式配置的正数，Oncall 新实例默认使用 0。

使用独立的容器配置路径，不直接套用宿主机绝对路径。业务仓库清单包含仓库名、地址、职责、可选本地缓存入口及默认分析 ref。`infra-workspace` 的关联资料可作为初始来源，机器人只消费资料，不运行其 setup、OMH Task 或交付工作流。其仓库规则与建议不得覆盖这里已经确认的产品行为。

### 5.2 话题、消息与执行

- Topic 增加 `businessWorkspaceId`，绑定聊天与规范化根消息；回复机器人的结果消息也必须回到同一个 Topic。
- 新增 TopicMessage：`topicId / messageId / sender / sourceTime / receivedOrder / items / trigger`。消息 ID 去重与 @ 入队在同一事务处理，消息重投不能多记上下文或多创建任务。
- InputItem 支持 `text / image / file / link`，包含来源消息与本地文件引用；原始日志留文件，按需读取，不把大文件全文塞进提示词。
- Job 记录本轮触发消息和上下文边界。建议以触发消息为边界冻结输入；后续补充保留到下次触发，避免排队时不断改变本轮请求。
- Topic 持久化 `paused` 与暂停原因。停止时先原子暂停话题，再请求中止活动轮次，防止活动轮结束与调度下一轮竞争；普通补充和普通 @ 不解除暂停。“继续”幂等解除暂停，先核对中断轮次的已执行结果，再按顺序处理保留请求，不复制旧 Job。
- 初次 @ 可能引用已存在告警或话题：通过可用的飞书接口补取同话题相关历史，不能只读取触发消息。获取不到的内容明确记录缺口。
- 请求元数据和用户内容分开传递；保留来源和发言者，避免把普通讨论当成对机器人的新执行指令。

### 5.3 案例

新增案例存储接口，按业务工作区查询。记录 `topicId / sourceMessageIds / summary / evidenceRefs / conclusions / verificationState / followUps / updatedAt`，允许同一案例追加、纠正和撤回结论，不以多轮重复回答创建大量重复案例。

案例写入与最终结果入库保持一致性；回复投递失败不能丢失案例，回复重试不能重复创建案例。与普通结构化运维日志分开存储，不通过日志打印原始消息。实际业务配置、原始案例、凭据与运行数据不提交到代码仓库。

第一版可用 SQLite 检索已有案例，不建设外部向量服务。先按工作区、错误标识和关键词召回，再由 Agent 核对适用条件。

## 6. 运行、异常与容器

一个专用容器内运行机器人网关、Codex 和必要业务工具；宿主机提供专用持久化目录。容器重建后保留 SQLite、Agent 会话、话题现场、业务配置和案例。

复用 Docker 的进程与文件系统边界，不引入额外安全平台；不通过挂载宿主 Docker socket、整个宿主目录或转发到宿主 Agent 来完成业务执行。凭据沿用已授权账号，以所需配置注入，飞书应用密钥仍仅由网关使用。群聊与私聊采用一致的业务操作授权规则；现有两种 Codex 执行模式需要在容器中验证可用性，不用特权容器规避 `unshare` 不兼容。

容器内优先复用现有 CLI 和业务技能（例如性能实验室、文档、代码与流水线工具），按实际需要接入。工具探测需区分“命令存在”“登录有效”“目标资源实际可读”，不能以安装成功代替可用。

异常处理约定：

1. 进程退出、SDK 明确失败、流提前终止：记录真实错误和已有结果，结束当前执行并通知话题。
2. 单次工具失败：Agent 可以调整查询路径；反复得到同一错误且无新证据时收敛，不能无限重复。正常长调用不因无文本进度直接判死。
3. 登录失效或资料不可访问：说明具体缺项与已有结论；不把工具失败写成业务根因。
4. 重启时，未开始的独立话题任务保留队列；已中断话题及其后续排队轮次暂停，等待用户明确继续，不能由队列中的旧请求变相自动续跑。
5. 恢复先核对外部操作是否已完成；响应丢失不等于操作未执行。不能整体重放重试任务、推分支、建 MR 等动作。
6. 保留已有状态卡与 outbox 重试。耗时可以展示，但不作为停止条件；分析完成与回复投递成功分别记录。
7. 用户停止或取消时暂停整个话题，保留未开始请求；只在明确继续后恢复。暂停不占用执行名额，重启不能解除暂停。停止请求到达与当前轮完成同时发生时，仍以持久化话题暂停状态阻止下一轮启动；已经完成的外部动作不作虚假撤销承诺。

保留运行中和等待恢复的话题现场；已结束话题的大文件清理沿用显式配置并单独核验，不能让目录清理一并删除共享案例或未交付补丁。

## 8. 验收与失败判定

沿用现有集成测试及本节真实操作清单，本次讨论稿不新建独立 YAML 用例文件。

实现阶段执行 `pnpm install --frozen-lockfile`、`pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build`；均需通过。测试使用临时 SQLite 和工作目录，不连接现网应用。验证结果见文末实施记录。

真实验收必须包含：

1. **私聊与群聊**：分别发起话题、引用原问题 @、补文字/截图/日志/链接；结果回到原话题。普通补充不启动轮次，再次 @ 能读到补充。同话题换人补充不丢上下文，新话题不串会话。私聊 @ 和话题交互必须在真实飞书客户端验证，不能仅凭模拟事件宣称可用。
2. **排队与并发**：6 个独立话题观测 5 并发和排队提示；同话题追加两次 @ 顺序执行。
3. **授权**：仅要求分析时，不重跑线上任务、不改代码、不建 MR；明确要求某动作后只执行该范围，回读实际结果，不重复要求授权。
4. **自主分析**：选择一个可通过日志/历史执行完成的案例，确认无需建分支、克隆仓库；另选确需代码的案例，按需获取指定版本并记录证据。
5. **长任务与中断**：正常长分析不因总耗时被终止；容器重启后可读到中断状态和现场，明确继续才能恢复，外部动作不重复。
6. **案例复用**：私聊案例可供同业务群参考；用户后续纠正更新记录；未验证推测有清晰标记。
7. **话题级停止**：话题内有一个活动轮次与至少两个排队请求时发送停止，活动轮终止后排队请求保持未执行，其他话题继续；重启后仍暂停。明确继续后核对中断现场并按序处理保留请求，无重复外部动作。

用户提供的首个真实样例是 Sheet 落地页 CI 任务中 `HTML_REPLAY_PEER_SNAPSHOT_NOT_READY`。验收应评估机器人如何取证、是否识别证据缺口、建议是否有依据，而非要求它必须找到 MR 缺陷或产出补丁。原始任务/流水线/MR 信息保留于运行材料，不复制到公共仓库测试夹具。

对该样例不得预设根因是环境或模板；现有告警只证明执行时断言失败。查不到根因可以交付有依据的阶段结论。“建议重试”“实际重试后恢复”“根因已证实”是三种不同结论。真实性能验收如需发生，必须沿用来源流水线实际 Base/Current、指标公式、过滤与判定规则，不使用 A/A、SD/CV 或自造统计门槛；本次计划整理不启动性能任务。
